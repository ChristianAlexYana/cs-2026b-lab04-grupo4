# Lienzo de diseño del sistema agéntico de CitaSalud Arequipa (E1)

Los tres issues salen de errores reales de `ServicioReservasDespues`, y cada uno tiene una prueba que lo reproduce: Issue 1 (se reserva dos veces el único cupo, `servicio.py`), Issue 2 (el DNI acepta letras y espacios, `externos.py`) e Issue 3 (se programa recordatorio de WhatsApp para una cita cancelada, `eventos.py`).

| Decisión | Elección para CitaSalud | Justificación |
|---|---|---|
| ¿Agente o flujo de trabajo? | Agente para resolver los tres issues; flujo fijo para el recordatorio de WhatsApp en producción. | Para corregir un error hay que explorar el código: no se sabe de antemano qué archivo leer ni cuántas veces correr las pruebas, así que el modelo decide el siguiente paso según lo que observa (Anthropic, 2024). En cambio, el envío del recordatorio siempre sigue los mismos pasos (verificar que la cita esté activa, programar, enviar) y no necesita que un modelo decida: un flujo fijo es más barato, rápido y predecible. La regla de la guía es usar la opción más simple que resuelva el problema. |
| Arquetipo | ReAct (sección 1.3, Tabla 3). | ReAct alterna pensar y actuar, y conviene para explorar un repositorio y localizar un error, que es lo que pide cada issue. No se eligió planificador-ejecutor porque los issues tocan uno o dos archivos y el plan completo no se conoce hasta leer el código. Tampoco reflexivo: ese arquetipo no razona entre pasos y aquí hay que observar el resultado de las pruebas. |
| Herramientas | Mínimas: `listar_archivos`, `leer_archivo`, `buscar`, `ejecutar_pruebas`, `editar_archivo` y `ejecutar_comando` limitado a pytest, radon cc, lint-imports y git status/diff. | Mínimo privilegio (sección 1.5, Tabla 5): pocas herramientas con alcance acotado, porque con muchas opciones el modelo elige peor. Todas las rutas se validan contra el sandbox y el agente no puede editar `tests/`, para que no «arregle» el error tocando la prueba. Sin red, sin credenciales y con DNI de prueba ficticios. |
| Memoria | Corto plazo: el historial de la corrida (pensamiento, acción y observación). Notas (`notas.md`) se agregan en E4. | Cada corrida parte de una copia limpia del repositorio, por lo que no se arrastra estado entre issues y el historial basta para tareas de pocos pasos (sección 1.6, Tabla 6). Las notas se incorporan después para medir si reducen pasos y contexto, sin suponerlo. |
| Coordinación | Agente único para los issues 1 y 3; actor-crítico (planificador, ejecutor y revisor de solo lectura, máximo 2 rondas) para el issue 2. | Albada (2025, cap. 8) recomienda empezar con un solo agente y agregar más solo cuando el problema lo pide: parsimonia (sección 1.7, Tabla 7). El issue 2 toca la validación de datos personales (RF-02, Ley 29733), donde un revisor independiente podría detectar un caso que el actor pase por alto. Si en E5 el revisor aprueba en la primera ronda, se dirá tal cual, y la conclusión pesará el costo adicional. |
| Rol humano | Revisor: el agente actúa y el humano aprueba en puntos de control (sección 1.8, Figura 6). | Es el primer uso del sistema y la confianza todavía es baja. El agente edita una copia (`agentes/trabajo/`), no el repositorio; una persona aplica el cambio, corre pytest y hace el commit. Con `--aprobar`, cada edición queda en pausa hasta responder «s» o «n» (Tabla 8). Ningún agente fusiona su propio cambio. |
| Control (contrato, política, pasos, rondas) | Contrato JSON validado antes de actuar; política de herramientas, comandos y rutas protegidas; máximo de 15 pasos para el ejecutor, 8 para el revisor y 2 para el planificador; máximo de 2 rondas; traza JSONL completa. | Cada decisión debe ser una acción o un final, nunca las dos (sección 1.4). Si el contrato se incumple, el error vuelve al modelo como observación («ERROR DE CONTRATO») y se anota, sin corregirlo a mano. El límite de pasos evita que el agente se ejecute indefinidamente. La traza permite auditar y medir cada corrida. |
